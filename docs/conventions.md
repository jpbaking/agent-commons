# Conventions

Every toolkit in this family follows the same contract. The vendor-neutral
authoring foundation lives in the external
[Portable Agent Authoring](https://github.com/jpbaking/portable-agent-authoring)
guides; this page defines the toolkit-family-specific conventions.

## Repository layout (per toolkit)

```text
AGENTS.md                              # authoritative project guidance
CLAUDE.md                              # generated bridge: @AGENTS.md
.agents/skills/<name>/SKILL.md         # authoritative portable Agent Skill
  scripts/ references/ assets/        # optional bundled resources
.claude/skills/<name>/SKILL.md         # generated byte-identical skill mirror
.clinerules/workflows/<name>.md        # generated thin Cline invocation shim
rules/shared/<name>.md                 # distributable user-global rule body
AGENT-INSTALL.md                       # merge-aware install contract
```

Edit only `AGENTS.md`, `.agents/skills/`, and `rules/shared/` by hand.
Regenerate the Claude mirrors and Cline shims after each skill change.
Portable `SKILL.md` frontmatter uses only `name` and `description`; bodies are
imperative and harness-neutral (no host command syntax, argument
interpolation, internal tool names, or vendor-only frontmatter).

## Install scopes

**Every toolkit installs user-global.** Skills, rules, and workflows live in
each harness's per-user discovery paths; installs never write into a
consuming project — not even its `.gitignore`. What lives in a project is
**project truth, committed**: `DOX.md` trees plus the root
`AGENTS.md`/`CLAUDE.md` anchors carrying the DOX shim (created or merged by
`dox-init`/`dox-upgrade`), `.goal-ledger/` records, copied `design/`
artifacts, `compose-helper.sh`/`.ps1`/`.env`, and generated agentic tests.
Truth is written by skills doing their job, never by installs.

Project-level adapter install remains an explicit opt-in (user request only)
for teams that want a toolkit pinned and shared in one repo.

Globally installed rules must self-gate on project state or a narrow request
intent (for example, a DOX root, `.goal-ledger/`, a compose-helper wrapper, a
served `design/` folder, or live-site testing). A deliberately machine-global
policy such as cross-cli-handshake must state that scope explicitly.

### Project-level targets (opt-in only)

| Artifact | Destination | Harness |
|---|---|---|
| Skills (authoritative) | `.agents/skills/<name>/` | Antigravity CLI, Codex, Pi |
| Skills (byte-identical generated mirror) | `.claude/skills/<name>/` | Claude Code and Cline |
| Invocation shim | `.clinerules/workflows/<name>.md` | Cline |
| Persistent rule | merge once into `AGENTS.md` | Antigravity CLI, Codex, Cline, Pi |
| Claude bridge | `CLAUDE.md` containing `@AGENTS.md` | Claude Code |

Never duplicate the same rule body in `.agents/rules`, `.claude/rules`, or
`.clinerules`: hosts combine detected rule types and would load it twice.
Opt-in project adapters are committed so a fresh clone has the same discovery
state. Root files are always merged; unrelated user content is preserved.

### User-global targets (the default for every toolkit)

Aligned on 2026-07-29 with the current Portable Agent Authoring harness
guides:

| Harness | Global skills | Global rules |
|---|---|---|
| Antigravity CLI (`agy`) | `~/.gemini/antigravity-cli/skills/<name>/` | merge a pointer block into `~/.gemini/GEMINI.md` |
| Codex | `~/.agents/skills/<name>/` | merge a pointer block into `~/.codex/AGENTS.md` |
| Claude Code | `~/.claude/skills/<name>/` | merge a pointer block into `~/.claude/CLAUDE.md` |
| Cline | `~/.cline/skills/<name>/` | merge a pointer block into `~/.agents/AGENTS.md` |
| Pi | `~/.agents/skills/<name>/` | merge a pointer block into `~/.pi/agent/AGENTS.md` |

All global skill copies stay byte-identical to the canonical source, exactly
like project adapters. `~/.agents/skills/` is one physical copy shared by
Codex and Pi. Store reusable global rule bodies under `~/.agents/rules/`, then
merge one marker-guarded pointer into each selected host's user-owned global
instruction file. Never overwrite those files or load the same rule through a
second host-native rules directory.

Never write behavioral Markdown to `.codex/rules` (that path is Codex's
command-execution policy, not guidance).

## The gitignore policy: hands off

Toolkits and installs **never touch a consuming project's `.gitignore`**.
Default installs are user-global, so nothing generated lands in projects.
When a team explicitly chooses project adapters, commit `AGENTS.md`,
`CLAUDE.md`, `.agents/skills/`, `.claude/skills/`, and
`.clinerules/workflows/` together; they are the repository's portable agent
interface.

What must never be gitignored (project truth): the root anchors
(`AGENTS.md` and `CLAUDE.md` carrying the DOX shim), `DOX.md`
trees, `.goal-ledger/`, generated agent tests (`*.agentic.spec.*`), the
project's used `design/` artifacts, and
`compose-helper.sh` / `compose-helper.ps1` / `compose-helper.env`.

If an existing ignore rule hides something a harness needs, warn with the
exact matching pattern and let the user decide — never edit their ignore
files. Projects installed under the old contract may still carry stale
marker-guarded ignore blocks and gitignored project adapters; removing those
is a manual, user-approved cleanup.

Fresh clones need no regeneration step: the committed anchors steer any
agent to `DOX.md` with zero tooling installed. Where docs reference an
optional toolkit, the wording is **offer-based, not imperative**:

> If the `<name>` skills are not available, they are an optional user-global
> install — offer to install them and proceed only if the user agrees.

## Install path

Installs are **agent-guided only** — there are no install scripts.
`AGENT-INSTALL.md` is the authoritative, idempotent contract:

1. **Acquire the sources** — `git clone` the toolkit repo (a tag/ref or fork
   URL may be given for pinning), download the repo/release zip, or use
   `gh repo clone` / `gh release download`; work from a temporary directory,
   never inside the target project.
2. **Survey** for collisions (project, compatibility, and global skill
   paths) and existing root instruction/ignore files.
3. **Install by copying** from the acquired sources to the user-global
   targets (project-level only on explicit user request).
4. **Merge marker-guarded pointer blocks** into user-owned global
   instruction files, validate byte-identical copies, clean up the
   temporary clone, and report every change. Never touch a project's
   `.gitignore`.

Re-running the same procedure updates an existing install.

## Invocation wording

Documentation says: *ask your agent to use the `<skill-name>` skill*.
Slash forms in Antigravity CLI, Claude Code, and Cline, Codex's `$` selector,
and Pi's `/skill:<skill-name>` form are host conveniences, never a
requirement—descriptions must support implicit activation.
